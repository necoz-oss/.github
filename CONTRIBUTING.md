# Contributing to Necoz

Thanks for considering a contribution. Necoz is a friendly open-source community, and first-time contributors are welcome here.

These notes apply across the [Necoz](https://github.com/necoz-oss) organization. When a project has its own contributing guide, setup steps, or review notes, follow those. Project instructions take precedence over this document.

## Who can contribute

Everyone. Any level of experience is welcome, including your first open-source contribution.

A typo fix, a clearer example, a bug report, and a code change are all real contributions.

## Ways to contribute

- **Bug reports** — describe what you expected and what happened
- **Suggestions** — share an idea for a small, useful improvement
- **Documentation** — fix, clarify, or extend docs and examples
- **Code** — implement a fix or feature the project is ready for
- **Discussions** — ask questions, share context, and help someone else get unstuck

Choose the kind of help you can offer. One useful contribution is enough.

## Finding an issue

Open issues labeled [`good first issue`](https://github.com/search?q=org%3Anecoz-oss+label%3A%22good+first+issue%22+is%3Aissue+is%3Aopen&type=issues) or [`help wanted`](https://github.com/search?q=org%3Anecoz-oss+label%3A%22help+wanted%22+is%3Aissue+is%3Aopen&type=issues) are a good place to start.

Before you begin:

1. Read that repository's README and any project-specific contributing notes.
2. Look through existing pull requests so two people are less likely to do the same work.
3. Leave a short comment on the issue if you plan to work on it. That comment is enough unless the repository asks people to wait for assignment.

If nothing on the list fits, open an issue and describe what you would like to do. For a larger change, a short proposal first can save you from rework.

## Opening a pull request

1. Follow the repository's instructions for forks, branches, and local setup when it has them.
2. Keep the change focused on one improvement.
3. Explain what changed and why it is useful.
4. Link a related issue when there is one.
5. Describe how you checked the change. If you could not run a check, say what you skipped and why.

Coding style, tests, commit messages, and branch names belong to each repository. Follow them when that repository documents them.

## Be a Good Cat 😸

Be kind. Be curious. Respect others.

Help when you can, ask when you need to, and keep feedback constructive. **Good code is great. Good cats are even better!**

In reviews, issues, and discussions:

- Assume other people mean well.
- Talk about the work, and keep comments specific.
- Disagree when it helps the project, and stay respectful while you do.
- Questions are welcome. Learning in public is part of contributing.

Please follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Need a pointer?

Start with the repository you care about. Its README should say what the project does and how to try it. If something is unclear, open an issue or discussion and ask. People here are glad to help you find the next step.

**Stay a Good Cat! 😸**
